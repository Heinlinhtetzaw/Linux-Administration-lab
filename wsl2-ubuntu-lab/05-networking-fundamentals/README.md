## 3. Essential Networking Concepts

An IP address identifies a network interface on a network. A MAC address is a link-layer address associated with an interface. A subnet divides an IP network, while a default gateway is the next hop used for destinations without a more specific route.

DNS resolves names such as `google.com` into addresses. TCP and UDP use ports to distinguish communication endpoints. TCP is connection-oriented; UDP is connectionless and does not guarantee delivery. Loopback addresses let a system communicate with itself. NAT translates network addresses and is relevant to my WSL2 network.

| Port | Common use |
|---|---|
| TCP 22 | SSH |
| TCP and UDP 53 | DNS |
| TCP 80 | HTTP |
| TCP 443 | HTTPS |

## 5. Practical Exercises

### Network Interface Investigation

I inspected `ip addr show`, `ip -br addr`, `ip link show`, and `hostname -I`. My abbreviated address listing was:

```output
lo               UNKNOWN        127.0.0.1/8 10.255.255.254/32 ::1/128
eth0             UP             172.30.245.70/20 fe80::215:5dff:feb3:ee8c/64
```

My main interface was `eth0`, with IPv4 address `172.30.245.70/20`. Its MAC address is masked for privacy. `lo` is the loopback interface; its `UNKNOWN` operational state is not by itself evidence of a problem.

### IP Address and Routing Investigation

I inspected the routing table:

```bash
ip route show
```

```output
default via 172.30.240.1 dev eth0 proto kernel
172.30.240.0/20 dev eth0 proto kernel scope link src 172.30.245.70
```

My default gateway was `172.30.240.1` through `eth0`, and `172.30.240.0/20` was the directly connected network. `ip route get 8.8.8.8` selected that gateway, interface, and source address. This is a route lookup; it does not send a test packet.

My WSL2 addresses and gateway can differ from my Windows host's. A WSL2 address should not automatically be assumed reachable from other computers on the physical network.

### Network Connectivity Testing

I sent four ICMP echo requests to each target. These are the recorded statistics lines:

| Target | Result |
|---|---|
| `127.0.0.1` | `4 packets transmitted, 4 received, 0% packet loss, time 3356ms` |
| Gateway `172.30.240.1` | `4 packets transmitted, 0 received, 100% packet loss, time 3069ms` |
| `8.8.8.8` | `4 packets transmitted, 4 received, 0% packet loss, time 3020ms` |
| `google.com` | `4 packets transmitted, 4 received, 0% packet loss, time 3186ms` |

My gateway did not answer the ping, but the later external IP ping succeeded. A missing ICMP response alone does not prove that a gateway is down; filtering or other behavior can prevent replies. The output does not identify the exact cause.

### DNS Resolution Investigation

I inspected `/etc/resolv.conf` and `resolvectl status`. My resolver configuration included:

```output
nameserver 10.255.255.254
```

The file said it was automatically generated by WSL. I used `getent hosts google.com`, `getent ahostsv4 google.com`, and `resolvectl query google.com`; they returned addresses. My report also resolved `example.com`. This verifies name resolution for those lookups at the time, not continuing reachability of every resolved address. I inspected `/etc/hosts` as well.

### Listening Port Investigation

I ran `ss -tuln` to inspect TCP and UDP sockets and `ss -tn state established` to inspect established TCP connections. My initial socket list included TCP and UDP port `53` on local resolver addresses and UDP port `323` on loopback. The established-connection check printed only its header at that moment.

I also ran `sudo ss -tuln`, but I omitted `-p`, so that general socket listing did not identify process owners. In the local server test below, I used `sudo ss -tlnp` and identified its Python process. A listening socket alone does not prove external accessibility; routing, NAT, and filtering may also matter.

### Local HTTP Server and Application Connectivity

I first tested an external HTTPS endpoint:

```bash
curl -I --max-time 10 https://google.com
```

The first two lines of the response were:

```output
HTTP/2 301
location: https://www.google.com/
```

This shows that the endpoint returned an HTTP redirect during that request. It does not establish that other sites or later requests will work.

I created `networking-lab/index.html` with the text `Linux Networking Lab - Server is running`. My first server started from the parent `linux-fundamentals-lab` directory, so it served a directory listing rather than my intended page. Changing directories in the client terminal did not change the server's working directory. I stopped the first server, changed into `networking-lab` in the server terminal, and started it again:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

During the first run, my other terminal identified a loopback listener and its process:

```output
LISTEN 0      5           127.0.0.1:8000      0.0.0.0:*    users:(("python3",pid=838,fd=3))
```
After restarting from the correct directory, my client received:

```bash
curl http://127.0.0.1:8000
```

```output
Linux Networking Lab - Server is running
```

The header request returned:

```output
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.12.3
Date: Wed, 25 Nov 2026 15:47:59 GMT
Content-type: text/html
Content-Length: 41
```

I stopped the restarted server with Ctrl+C. A subsequent client request returned:

```output

```

The subsequent `ss -tln | grep ':8000'` produced no output. These checks show the HTTP application was unavailable after the stop; I did not repeat the loopback ping after stopping it. The Python server was bound to loopback for this exercise and is intended for practice, not production deployment.

## 6. Basic Network Troubleshooting Methodology

I can investigate an inaccessible application in stages: check the interface, inspect routes and the gateway, test external IP connectivity, check name resolution, inspect relevant listening sockets, and test the application itself. Service status can add context when the application runs locally. Each result is a clue; a failed ping or timed-out request alone does not identify the root cause.

## 8. Errors and Troubleshooting

- I initially ran `ping -c 4 via 172.30.240.1`. `via` is part of the route output, not the gateway argument; the command returned `ping: via: Name or service not known`. I retried with the address alone.
- The gateway ping had 100% packet loss. External IP connectivity succeeded afterward, so I cannot conclude from the ping alone that the gateway was down.
- My first HTTP server served the wrong directory. I corrected the server's working directory and verified the intended page. Changing the client's working directory alone did not affect what the server served.
- I omitted `-p` from the general privileged socket listing, leaving the owners of those sockets unverified. The process for the first HTTP server was identified separately.
- The report's `curl` request to `example.com` timed out; I have not identified its cause or verified a successful retry.
